## Завдання 1. Одноразові запрошення на подію — `HashSet<string>`

На вході до події перевіряють ID запрошення. Кожне запрошення можна
використати **лише один раз**, а скасовані запрошення недійсні.
Для кожної спроби входу поверніть `true`, якщо відвідувача можна пропустити,
або `false` — якщо ні.

- `invited` містить унікальні запрошення. `cancelled` — скасовані ID;
  скасування невідомого ID нічого не змінює.
- `attempts` містить спроби входу в порядку надходження.
- Успішний вхід використовує запрошення. Наступний вхід із тим самим ID відхиляється.
- Використайте `HashSet<string>` для доступних запрошень. Результат —
  `List<bool>` із тією самою кількістю елементів, що й `attempts`.
- Кожен масив містить від 0 до 10 000 елементів.
- **Очікувана складність:** O(n) часу та O(n) пам'яті, де n — загальна кількість вхідних елементів.

### Приклади з поясненням

## Завдання 2. Список файлів для синхронізації — `HashSet<(string, string)>`

Програма порівнює локальні файли з файлами на сервері. Для кожного файлу
відомі шлях `Path` і готовий рядок хешу `Hash`. Поверніть шляхи файлів,
які потрібно завантажити: **нові або з іншим вмістом**.

- Усередині кожного вхідного списку шляхи унікальні.
- Файл не потребує завантаження лише тоді, коли локально є такий самий шлях
  із таким самим хешем. Однаковий хеш за іншим шляхом не підходить.
- Збережіть порядок серверного списку `remote`. Локальні файли, яких немає

- Використайте `HashSet<(string Path, string Hash)>` для локальних версій.
  Обчислювати хеші чи читати справжні файли не потрібно.
- Кожен масив містить від 0 до 10 000 записів.
- **Очікувана складність:** O(n + m) часу та O(n + m) пам'яті.

## Завдання 6. Вкладені зміни налаштування — `Stack<int>`

Редактор змінює ціле числове налаштування. Користувач може почати групу змін,
зберегти її або скасувати. Групи можуть бути вкладеними.
Поверніть **кінцеве значення налаштування** після всіх команд.

- `Begin` відкриває групу й запам'ятовує поточне значення.
- `Add` додає `Amount` до поточного значення; дозволена і поза групою.
- `Commit` закриває останню відкриту групу, зберігаючи зміни.
- `Rollback` закриває останню відкриту групу та відновлює значення,
  яке було під час її `Begin`.
- Збереження внутрішньої групи не захищає її зміни від скасування зовнішньої.
- Використайте `Stack<int>` для збережених значень. Послідовність команд правильна:
  кожен `Commit` / `Rollback` має відкриту групу, наприкінці всі групи закриті.
- До 10 000 команд; `initial` та `Amount` — від `-1000` до `1000`.
- **Складність:** O(n) часу та O(n) додаткової пам'яті.

## Завдання 7. Однакова висота стосів коробок — `Stack<int>`

зверху; переставляти або додавати їх не можна. Знайдіть **найбільшу спільну
висоту**, якої можна досягти.

- Кожен масив містить висоти коробок **від дна до вершини**: останній елемент — верхній.

- **Складність:** O(n + m + k) часу та пам'яті. Не обчислюйте повні суми стосів

## Завдання 9. Пакетна відправка подій — `Queue<TelemetryEvent>`

Пристрій накопичує події та надсилає їх пакетами. Пакет відправляється,
коли зібрано `maxItems` подій або минуло `window` одиниць часу від першої
події пакета. Визначте **склад пакетів і час кожного відправлення**.

- Події вже впорядковані за `Time`; за однакового часу зберігайте вхідний порядок.
  ID унікальні. Використайте `Queue<TelemetryEvent>`.
- Відлік часу починається з першої події нового пакета й не пересувається
  після надходження наступних подій.
- Подія рівно на часовій межі ще входить до поточного пакета, якщо є місце.
- Повний пакет відправляється в момент надходження його останньої події.
  Неповний — у момент `час першої події + window`, навіть якщо вхід уже закінчився.
- Порожні пакети не створюйте. Час моделюйте переходами між подіями,
  без циклу по кожній одиниці часу.
- До 10 000 подій; `Time` — від 0 до 1 000 000,
  `1 <= maxItems <= 100`, `1 <= window <= 1000`.
- **Складність:** O(n) часу та O(n) пам'яті.

## Завдання 10. Черга друку з пріоритетами — `Queue<PrintJob>`

Принтер бере заявку з початку черги. Якщо серед решти є заявка з **вищим
пріоритетом**, поточна повертається в кінець. Інакше принтер друкує її та
видаляє з черги. Поверніть порядок надрукованих ID.

- Більше число означає вищий пріоритет. Рівний пріоритет не заважає друку.
- Усі заявки вже перебувають у початковій черзі; нові під час обробки не надходять.
- Перенесення в кінець впливає на подальший порядок. Не замінюйте процес
  сортуванням: воно може дати інший порядок для однакових пріоритетів.
- Використайте `Queue<PrintJob>`. Дозволено переглядати чергу через `foreach`,
  щоб знайти вищий пріоритет, але не змінюйте її всередині цього обходу.
- Не використовуйте `PriorityQueue`, `Sort` або `OrderBy`.
- До 1000 заявок; ID унікальні; пріоритет — від 1 до 9.
