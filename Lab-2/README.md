## Завдання 1. Звірка фактичної поставки з накладною — `HashSet<string>`

На складі є список очікуваних ідентифікаторів коробок `expected` та журнал
сканування отриманих коробок `scanned`. Сканер може кілька разів прочитати ту
саму коробку. Сформуйте звіт про те, **чого бракує, що зайве і що сканували повторно**.

- `expected` містить унікальні ID. Обидва масиви мають від 0 до 10 000 елементів.
- `Missing`: очікувані ID, яких немає серед сканувань, у порядку накладної.
- `Unexpected`: ID, яких немає в накладній, без повторів, у порядку першого сканування.
- `Repeated`: ID, які сканували щонайменше двічі, кожен лише один раз,
  у порядку другого сканування. Це стосується і очікуваних, і зайвих коробок.
- Використайте `HashSet<string>` для перевірки належності та повторів;
  `List<string>` — для впорядкованих частин звіту.
- Не використовуйте готові LINQ-операції `Distinct`, `Except`, `Intersect` або `GroupBy`.
- **Очікувана складність:** O(n + m) часу та O(n + m) пам'яті, де n і m — довжини масивів.

### Приклади з поясненням

| Накладна; сканування | Результат | Пояснення |
|---|---|---|
| `[A, B, C]`; `[B, B, D, A, D]` | Бракує `[C]`; зайві `[D]`; повтори `[B, D]` | `C` не надійшла, `D` не замовляли, а `B` і `D` сканували двічі |
| `[A, B]`; `[B, A]` | Усі три списки порожні | Усі очікувані коробки надійшли по одному разу; порядок сканування неважливий |
| `[]`; `[X, X, X]` | Бракує `[]`; зайві `[X]`; повтори `[X]` | Навіть після трьох сканувань `X` записується до кожної категорії лише один раз |

## Завдання 2. Вільний час для зустрічі — `List<TimeSlot>`

Календар містить зайняті проміжки робочого дня. Знайдіть **усі максимальні
вільні проміжки**, у яких можна провести зустріч тривалістю хоча б `minDuration`
хвилин. Поверніть їх за зростанням часу початку.

- Час задано цілими хвилинами від початку доби: `0 <= dayStart < dayEnd <= 1440`.
  Наприклад, `540` — це 09:00. `1 <= minDuration <= 1440`.
- Проміжок `[Start, End)` включає початок і не включає кінець;
  його тривалість дорівнює `End - Start`.
- Зайняті проміжки повністю належать робочому дню, мають додатну тривалість,
  але можуть бути невпорядкованими, перетинатися, вкладатися один в один або торкатися.
- Поверніть вільні проміжки цілком, а не всі можливі варіанти початку зустрічі.
  Проміжок рівно `minDuration` хвилин підходить; коротший — ні.
- Вхід містить від 0 до 10 000 проміжків. Використайте `List<TimeSlot>`;
  дозволено сортувати копію списку через `Sort`.
- **Складність:** O(n log n) часу та O(n) додаткової пам'яті.

## Завдання 3. Власний час вкладених операцій — `Stack<T>`

Програма записує в журнал початок і завершення операцій. Одна операція може
викликати іншу. Для кожної операції визначте **власний час виконання** — час
між її початком і завершенням без часу, витраченого на вкладені операції.
Це допомагає знайти повільну частину програми, не рахуючи той самий час двічі.

- `Start` і `End` позначають часові межі: операція від `2` до `5` триває `3`
  одиниці часу. Додавати одиницю до різниці не потрібно.
- Журнал відсортований за часом; за однакових часових позначок зберігайте порядок записів.
- Кожна операція має унікальне ім'я, один `Start` і один `End`. Вкладеність
  правильна: завершується остання з розпочатих незавершених операцій.
  Можливі кілька окремих операцій верхнього рівня та нульові тривалості.
- Поверніть `OperationTime` у порядку завершення операцій.
- Використайте `Stack<T>` для збереження даних активних операцій.
  Тип елемента стека оберіть самостійно. Рекурсію не використовуйте.
- Журнал містить від 0 до 20 000 записів; час — від 0 до 1 000 000.
- **Складність:** O(n) часу та O(n) пам'яті разом із результатом.

### Приклади з поясненням

У таблиці `S` означає `Start`, а `E` — `End`; число після літери — час події.

| Журнал | Результат у порядку завершення | Пояснення |
|---|---|---|
| `Main S0, Read S2, Read E5, Main E8` | `Read: 3; Main: 5` | `Read` працює 3 одиниці, а власний час `Main` — `8 - 3 = 5` |
| `Main S0, Check S1, Check E4, Save S4, Save E6, Main E10` | `Check: 3; Save: 2; Main: 5` | У `Main` дві послідовні вкладені операції; їхні 5 одиниць не належать до власного часу `Main` |
| `A S0, B S1, C S2, C E4, B E7, A E10` | `C: 2; B: 4; A: 4` | `B` триває 6 одиниць разом із `C`; з часу `A` віднімається весь цей вкладений проміжок |

## Завдання 4. Перевірка журналу входів і виходів — `HashSet<string>`

Система доступу зберігає події `Enter` і `Exit` для працівників. На початку
будівля порожня. Знайдіть помилкові події, визначте, хто залишився всередині,
та обчисліть **максимальну кількість людей, які одночасно перебували в будівлі**.

- Повторний `Enter` для людини, яка вже всередині, — помилка.
- `Exit` для людини, якої немає всередині, — помилка.
- Помилкова подія не змінює стан будівлі й не впливає на максимум.
  Подальші події продовжуйте обробляти.
- `InvalidEvents` містить номери помилкових подій **від 1** у порядку журналу.
  `Inside` — множина людей, які залишилися. `MaxInside` — найбільша одночасна кількість.
- Повторний вхід після правильного виходу дозволений. ID `A` і `a` різні.
- Використайте `HashSet<string>` для поточного стану. У журналі від 0 до 10 000 подій.
- **Очікувана складність:** O(n) часу та O(n) пам'яті. Сортування ID у шаблоні
  потрібне лише для однакового порядку друку, а не для алгоритму.

### Приклади з поясненням

| Журнал | Результат | Пояснення |
|---|---|---|
| `A Enter, B Enter, A Enter, B Exit, C Exit` | Помилки `[3, 5]`; всередині `[A]`; максимум `2` | `A` увійшла повторно, а `C` не входила. Найбільше людей було після другої події |
| `A Enter, A Exit, A Exit` | Помилки `[3]`; всередині `[]`; максимум `1` | Другий вихід не змінює вже порожню будівлю |
| Журнал порожній | Помилки `[]`; всередині `[]`; максимум `0` | Жодної події не відбулося |

## Завдання 5. Черга заявок із граничним часом очікування — `Queue<SupportTicket>`

Один оператор послідовно обробляє заявки. Кожна заявка має час надходження,
тривалість обробки та максимально дозволений час очікування. Побудуйте розклад:
для кожної заявки поверніть час початку й завершення або позначте її простроченою.

- Заявки вже впорядковані за `Arrival`; за однакового часу зберігайте вхідний порядок.
  ID заявок унікальні. Використайте `Queue<SupportTicket>` та порядок FIFO.
- Оператор спочатку вільний у момент `0`. Після початку обробки він працює
  без перерви `Duration` одиниць часу; наступна заявка чекає.
- Якщо черга очікує на майбутнє надходження, оператор простоює до цього часу.
- Якщо на момент можливого початку заявка чекала **більше ніж `MaxWait`**,
  пропустіть її. Прострочена заявка не витрачає час оператора.
  Очікування рівно `MaxWait` допустиме; тривалість самої обробки до очікування не входить.
- Результат зберігає вхідний порядок і містить усі заявки.
  Для простроченої заявки `Start` та `End` дорівнюють `null`.
- Вхід містить від 0 до 10 000 заявок; `Arrival` і `MaxWait` — від 0 до 1 000 000,
  `Duration` — від 1 до 1000. Час задається цілими числами.
- **Складність:** O(n) часу та O(n) пам'яті. Не перебирайте час по одиницях.
